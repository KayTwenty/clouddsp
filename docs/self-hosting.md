# Self-hosting cloudDSP

Run the whole thing yourself: the website, the job queue, file storage and
the GPU worker. Pick the setup that fits.

| Setup | For | Needs |
|---|---|---|
| [One command](#one-command) | Your own computer with an NVIDIA GPU | Node.js 22+, uv, ffmpeg |
| [Docker Compose](#docker-compose) | A home server or always-on machine | Docker, NVIDIA Container Toolkit |
| [Add more GPUs](#more-gpus) | Spreading work over several machines | uv and ffmpeg on each |

Out of the box everything is stored on the machine (jobs as JSON files, files in
`.data/storage`) and uploads and results are deleted after 48 hours. You can
switch to Postgres and S3-compatible storage at any point with
[environment variables](#settings).

## One command

```bash
git clone https://github.com/KayTwenty/clouddsp.git
cd clouddsp
npm install
npm run selfhost
```

Then open http://localhost:3000.

`npm run selfhost`:

1. builds the website on the first run,
2. creates a worker token in `.data/worker-token`,
3. starts the website and a GPU worker together, with both logs in one window.

The worker detects your GPU with `nvidia-smi` and installs the matching
PyTorch build the first time (a few GB):

| GPU | PyTorch build | NVIDIA driver |
|---|---|---|
| GTX 10-series (Pascal) | CUDA 12.6 | 560+ |
| RTX 20 / 30 / 40-series | CUDA 12.8 on driver 570+, otherwise 12.6 | 560+ |
| RTX 50-series (Blackwell) | CUDA 12.8 | 570+ |
| No NVIDIA GPU | CPU (works, much slower) | |

Use another port with `npm run selfhost -- --port 8080`. Stop everything with
Ctrl+C.

## Docker Compose

Requires Docker and the
[NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
so containers can use the GPU.

1. Copy `.env.example` to `.env` and set a `WORKER_TOKEN`:

   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```

   On a GTX 10-series card also set `CLOUDDSP_TORCH=cu126`.

2. Start it:

   ```bash
   docker compose up -d --build
   ```

3. Open http://localhost:3000.

Data lives in the `clouddsp-data` volume and the downloaded model weights in
`model-cache`, so rebuilding or restarting keeps both. `docker compose logs -f`
shows what the worker is doing.

### Putting it on the internet

Put a reverse proxy (Caddy, nginx, Traefik, Cloudflare Tunnel) in front of port
3000 with HTTPS, and set `NEXT_PUBLIC_SITE_URL` to the public address. Uploads
go through the site in this mode, so allow request bodies up to 200 MB in the
proxy. A public instance should also raise the defaults that matter for
strangers: keep `RETENTION_HOURS` short and watch disk space.

## More GPUs

Any machine with a GPU can join an instance, local or remote. On that machine:

```bash
git clone https://github.com/KayTwenty/clouddsp.git
cd clouddsp
```

```powershell
$env:CLOUDDSP_URL = "http://your-server:3000"
$env:WORKER_TOKEN = "<the instance's worker token>"
uv run --no-project worker/start.py
```

(On Linux/macOS: `CLOUDDSP_URL=... WORKER_TOKEN=... uv run --no-project worker/start.py`.)

Workers only make outgoing requests, so they work from behind NAT. Run one per
GPU; jobs are handed out so no two workers take the same one, and a job whose
worker disappears goes back in the queue after two minutes. Set `WORKER_NAME`
to label it on the `/status` page.

A machine with both a GTX 10-series and an RTX 50-series card needs one worker
per GPU (`CUDA_VISIBLE_DEVICES=0` for one, `=1` for the other), since no single
PyTorch build supports both.

## Settings

All optional. Put them in `.env` (or `.env.local`); `.env.example` lists every
one with comments.

| Variable | Default | What it does |
|---|---|---|
| `WORKER_TOKEN` | generated by `selfhost` | Secret shared by the site and its workers. Required in production. |
| `WORKER_NAME` | GPU model | Worker label on `/status`. |
| `CLOUDDSP_TORCH` | detected | Force `cu126` or `cu128`. |
| `DATABASE_URL` | JSON files | PostgreSQL for the job queue. Needed when running the site on several servers. |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` | built-in storage | Any S3-compatible storage (MinIO, AWS S3, Backblaze B2, Wasabi). |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` | | Cloudflare R2 shorthand for the above. |
| `STORAGE` | | `local` forces built-in storage even if keys are set. |
| `RETENTION_HOURS` | `48` | How long built-in storage keeps files. `0` keeps them forever. |
| `NEXT_PUBLIC_SITE_URL` | `http://localhost:3000` | Public URL for links, sitemap and social cards. |
| `NEXT_PUBLIC_SOURCE_URL` | this repository | "Source code" link in the footer. |

### Postgres

Set `DATABASE_URL` to a `postgres://` URL, then create the tables once:

```bash
npx prisma migrate deploy
```

Run the same command after updating cloudDSP if `prisma/migrations` changed.

### S3-compatible storage

Create a private bucket and an access key for it, then set the `S3_*`
variables. Browsers upload and download straight from the bucket, so it needs
a CORS rule allowing your site's origin (methods `GET`, `PUT`, `HEAD`, headers
`Content-Type` and `Range`, exposing `Content-Length`, `Content-Range` and
`ETag`). Add a lifecycle rule that deletes objects after a couple of days;
`RETENTION_HOURS` only applies to built-in storage.

With Docker Compose, add the variables you use to the `web` service's
`environment` in `compose.yaml`.

## Troubleshooting

- **The worker says the GPU isn't supported by this PyTorch build.** It prints
  the right `--extra` to use. With Docker, set `CLOUDDSP_TORCH` in `.env` and
  rebuild.
- **Uploads fail when using object storage.** Almost always the bucket's CORS
  rule: the site's exact origin (scheme, host and port) must be listed.
- **Workers get 401 Unauthorized.** The worker's `WORKER_TOKEN` must match the
  site's exactly.
- **Windows: the production build fails while prerendering.** Run commands from
  the folder's real name and casing (for example `clouddsp`, not `cloudDSP`).
